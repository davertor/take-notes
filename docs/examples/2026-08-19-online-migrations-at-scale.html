Online migrations at scale

Feb 2, 2017 · 6 min read

Open original →

Executive summary

Stripe needed to move hundreds of millions of subscription records out of an array field on the Customer object and into a table of their own, without downtime and without a single inconsistent read. This post describes the four-phase dual-writing pattern they used: write to both stores, move reads to the new one, move writes to the new one, then delete the old data. The interesting content is not the pattern itself — which is widely known — but the two things that made it survivable at scale: doing the expensive "which objects still need migrating?" work offline on Hadoop snapshots instead of querying production, and using GitHub's Scientist library to run both code paths in production and alert on any disagreement before trusting the new one. The whole approach is built around never changing more than a few hundred lines at a time.

The one takeaway

A large data migration is safe when every step is independently reversible and independently verifiable — dual-write, then dual-read-and-compare, then cut over — rather than attempting one large atomic change and hoping.

Key points

  • The scale problem is arithmetic, not engineering cleverness — at one second per object, a hundred million objects takes over three years sequentially. Any approach that processes records one at a time against the production database is dead on arrival, which is what forces the offline and parallel design that follows.
  • Uptime was a constraint, not a goal — Stripe performs infrastructure upgrades online rather than in maintenance windows, so the Subscriptions service had to stay at 100% throughout. That single decision rules out every simpler migration strategy.
  • The four phases exist to keep the two stores consistent at every moment — dual write, switch reads, switch writes, delete. At no point is there a state where one store holds truth the other lacks, which is what makes each phase safe to pause or reverse.
  • Backfilling is done lazily first, then swept — existing records are copied whenever they happen to be updated, so ordinary traffic does most of the work for free. Only what remains after that needs an explicit migration job.
  • Finding the records is the expensive part, so it happens offline — identifying every subscription needing migration would mean many queries against production. Instead they run MapReduce over database snapshots on a Hadoop cluster, producing a list of IDs with zero production impact.
  • Scientist turns "is this safe?" into a measurement — GitHub's library runs both the old and new read paths in production and alerts when the results differ, with errors in the experimental path isolated from the real response. Correctness is observed under real traffic rather than argued about in review.
  • Changing the write paths is the hard phase, not the read paths — subscription logic (updates, prorations, renewals) spanned thousands of lines across multiple services. Their mitigation is to isolate each code path into the smallest unit that can be changed and verified alone.
  • They made the old field impossible to use by accident — the subscriptions accessor is replaced with one that raises a hard error. Anything still reaching for the old model fails loudly instead of silently reading stale data.
  • Deletion is also incremental — the old array is emptied whenever a subscription is loaded, with a final Scalding job sweeping up whatever remains. The same lazy-then-sweep shape as the backfill, run in reverse.

Concepts

  • Dual writing — writing every change to both the old and new stores during a migration, so neither goes stale and either can serve as the source of truth while you decide.
  • Backfill — copying the records that already existed before dual writing began. Dual writing handles the future; backfilling handles the past.
  • Scientist — GitHub's Ruby library for running an experimental code path alongside the real one in production, comparing results and reporting mismatches without affecting the response.
  • MapReduce / Scalding — the offline distributed-processing model, and the Scala library Stripe uses to write those jobs. Here it answers one question cheaply: which records still need migrating?
  • Lazy migration — copying a record when it happens to be touched by normal traffic, so the migration cost is spread across ordinary requests instead of concentrated in a batch job.

How it works

  1. Create the new table. Begin writing every new subscription to both it and the old Customers table, ramping the duplicated percentage up slowly while watching production metrics.
  2. Copy existing records lazily — whenever a subscription is updated, write it to the new table too.
  3. Run a Scalding job over database snapshots to list every subscription still missing, migrate those in parallel, then re-run the job to confirm nothing is left.
  4. Wrap reads in a Scientist experiment reading from both tables and alerting on any mismatch. Once results agree consistently, switch reads to the new table.
  5. Reverse the write order — new table first, old table as the archive — then refactor each write path one small unit at a time, with Scientist still watching.
  6. Stop writing to the old store, make the old accessor raise, empty the array lazily, and sweep up the remainder with a final job.

  • Why are migrations hard? — the three constraints: scale, uptime, and accuracy across a codebase that reads the table everywhere
  • A pattern for online migrations — the four-step dual-writing pattern stated up front
  • Our example migration: Subscriptions — how a single subscription field became an array and then became a problem
  • Part 1: Dual writing — ramping up duplicate writes, lazy copying, and the offline Hadoop backfill
  • Part 2: Changing all read paths — Scientist experiments comparing both tables under production traffic
  • Part 3: Changing all write paths — the hardest phase, and why it is done in the smallest possible units
  • Part 4: Removing old data — hard-failing the old accessor, lazy deletion, final sweep
  • Conclusion — the four practices they credit: phased strategy, offline processing, incrementalism, observability

Going deeper

  • No numbers on how long it took. The post opens with the arithmetic that makes naive migration impossible, then never says how long the real one took, how much the dual writes cost in production latency, or how many Scientist mismatches were found. The pattern is well argued; its price is not reported.
  • The tooling assumptions are heavy. Snapshots in a Hadoop cluster and a mature experiment framework are what make this affordable. A team without offline snapshots faces the expensive-query problem the post sidesteps, and that constraint is not addressed.
  • It is from 2017 and the ecosystem moved. Scalding and this MapReduce workflow would likely be Spark or a warehouse query today, and Scientist has ports in most languages. The shape — dual write, compare under real traffic, cut over incrementally — is what aged well.
  • Try next: read github/scientist's README, which is short, and note how much of this post's safety comes from that one idea: run both paths, compare, and let production tell you whether you were right.
